## 3. 生成するドキュメント種別（5種類）

### 3-1. ビジネス要件定義書（BRD）

- **参考資料**: ビジネス概要書_v5.docx
- **ファイル形式**: A4 Word（.docx）
- **命名規則**: `{システム略称}_BRD_v{バージョン}.docx`（例: SBDS_BRD_v1.0.docx）

**必須記載項目**:
1. 文書管理表（バージョン・作成日・承認者）
2. 事業背景・解決する社会課題
3. ビジネスゴール・KPI（定量目標値）
4. ターゲットユーザー・ステークホルダー定義
5. ビジネス機能要件一覧（Must/Should/Could分類）
6. 収益モデル・コスト構造
7. 制約条件・前提条件
8. 不滅憲章との整合性確認チェックリスト

**レイアウト規則**:
- A4縦・余白上下左右20mm
- フォント: 游ゴシック 10.5pt本文・見出し12pt Bold
- 空白行・余白を設けない高密度レイアウト
- 表は全幅（width: 9026 DXA）で統一
- ページ番号・フッターにシステム名・バージョン・Confidentialを記載

### 3-2. システム要件定義書（SRS）

- **参考資料**: Doc2_システム要件定義書_SRS_v4.docx
- **ファイル形式**: A4 Word（.docx）
- **命名規則**: `{システム略称}_SRS_v{バージョン}.docx`

**必須記載項目**:
1. 文書管理表
2. システム全体像・対象領域
3. 5つの絶対条件（Ver.14.2の不変制約を各システム向けに記載）
4. 機能要件一覧（ID・機能名・詳細・優先度Must/Should/Could）
5. 非機能要件（性能・可用性・セキュリティ・拡張性）
   - 処理速度: 0.7秒以下（TMS-DRV-001）または500ms以下（その他）
   - インフラコスト: 1個口¥0.5円以下
   - PII物理隔離（DevSepOps）
6. 技術スタック定義
7. 外部API・連携システム一覧
8. データモデル概要
9. セキュリティ要件（HMAC-SHA256・AES-256・MFA）

### 3-3. シーケンス図集（SEQ）

- **ファイル形式**: A4横 PowerPoint（.pptx）
- **命名規則**: `{システム略称}_SEQ_v{バージョン}.pptx`

**必須記載項目**（各主要フローにつき1図）:
1. 正常系メインフロー（ユーザー操作→バックエンド→DB→レスポンス）
2. 異常系・エラーハンドリングフロー
3. 外部API連携フロー（Keepa / LINE / Stripe / HubSpot / 国税庁API等）
4. 認証フロー（JWT / MFA）
5. データ同期・キャッシュフロー（IndexedDB niceeze_cache_v142）

**図の作成規則**:
- アクター配置（左から）: ユーザー → フロントエンド → バックエンド → DB → 外部API
- 矢印: 同期（実線→）・非同期（破線→）を明示
- 重要判定ロジックはAlt/Loopフレームで囲む
- スライド1枚に1フロー
- カラー: NiceEzeブランドカラー（濃紺 #1a3a5c・オレンジ #f5a623・白）

### 3-4. 画面設計書（UI）

- **ファイル形式**: A4縦 PowerPoint（.pptx）
- **命名規則**: `{システム略称}_UI_v{バージョン}.pptx`

**必須記載項目**:
- 画面ID・画面名・対象ユーザー・アクセス権
- ワイヤーフレーム/モックアップ（図解必須・テキストのみ不可）
- LAYOUT_MASTER.mdの配置仕様に完全準拠
- font-mono tabular-nums tracking-tight適用箇所を明示
- 上部・中央・下部エリア区分を視覚的に明示
- 入力フィールド仕様（型・バリデーション・必須/任意）
- ボタン・アクション定義
- エラー表示・警告バナー仕様
- 画面遷移図（冒頭サマリースライド1枚）

**重要制約**:
- GeminiはUI設計・実装に一切関与しない
- LAYOUT_MASTER.mdとの差異がゼロであること
- レイアウト変更は必ず松浦CEO承認後にLAYOUT_MASTER.mdを先に更新すること

### 3-5. フェーズ管理書（PHASE）

- **ファイル形式**: A4横 PowerPoint（.pptx）
- **命名規則**: `{システム略称}_PHASE_v{バージョン}.pptx`

**必須記載項目**:
1. 文書管理表・開発基本方針
2. フェーズ全体マップ（Gate 0〜7対応）

| Gate | 内容 | 目標期日 |
|:---|:---|:---|
| Gate 0 | 要件凍結・環境構築 | 2026年7月末 |
| Gate 1 | SBDS初期実装・DevSepOps構築 | 2026年9月末 |
| Gate 2 | SURPLUS SHIFT・i18n・DWG判断 | 2026年11月末 |
| Gate 3 | Marketing・スケジューラー | 2027年1月末 |
| Gate 4 | Cloud Run proxy・本番移行 | 2027年2月末 |
| Gate 5〜7 | スケールアウト・外部連携 | 別途策定 |

3. 各フェーズの工数内訳（役割・人月・費用・AI活用による削減率）
4. 予算管理表（総開発費¥2,844万/補助金活用後¥1,293万）
5. 補助金活用計画（IT導入・事業再構築・都DX・人材開発）

## 4. バージョン管理ルール

- 初版: v1.0
- 機能追加・仕様変更: マイナーバージョンアップ（v1.1, v1.2…）
- Gate通過時の大改訂: メジャーバージョンアップ（v2.0…）
- 各ドキュメントのフッターおよびファイル名にバージョンを必ず明記
- 旧バージョンはGoogle Driveのarchive/サブフォルダへ移動
- Gitリポジトリの`docs/{システム略称}/`にも同一ファイルをコミット

## 8. 不明点の報告方法

仕様が未確定、または実装不可能な制約に直面した場合:
1. ドキュメント内の該当箇所に **【松浦CEO要件定義待ち】** と明記する
2. `CHANGELOG_JA.md`に不明点の詳細・判断に必要な選択肢を記載する
3. 次回報告時にCEO補佐（Claude）へ整理した形で提出する

> でっち上げ・曖昧な記載・空欄の放置は不滅憲章違反として即時差し戻す。
